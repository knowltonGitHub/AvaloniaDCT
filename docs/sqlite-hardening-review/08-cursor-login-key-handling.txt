HOW LOGIN USES THE KEY

There is no separate “database password.” What the user types is the
SQLCipher passphrase.

Debug (default)
Same as today: open bin\Debug\...\CBDB.db with no password, then SELECT the
user row. Wrong password → no row → “Invalid username or password.”

Hardened (DCT_HARDENED=1 or Release)
1. Build the connection with Password = the typed passphrase (plain text;
   SQLCipher does PBKDF2 itself).
2. Open() and run a cheap query (for example SELECT COUNT(*) FROM
   sqlite_master or load the user row).
3. Success → password was correct. Cache that passphrase (or the
   open-session factory) on UserSession and use it for every later
   connection. Do not derive again.
4. SqliteException with code 26 (SQLITE_NOTADB) → treat as invalid
   password. Show the same login error, not a crash or “database corrupt.”
5. Other IO/permission errors → real failure message, not “wrong password.”

Username still matters if you ever have more than one person: after a
successful open, check that the username exists. For a single-user DCT,
successful decrypt is enough; the username field can stay for compatibility.
